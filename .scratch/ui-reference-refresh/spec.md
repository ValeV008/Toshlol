# UI Reference Refresh and Transaction Splits

Status: ready-for-agent

## Problem Statement

The implemented app follows an earlier charcoal-and-yellow design rather than the reference app the user now wants to copy. Its navigation tabs, direct-to-edit Transaction rows, expanded editor fields, and always-visible Budget editor differ from the supplied screenshots. The user wants the new reference app's red/green/blue headers, off-white backgrounds, flatter activity lists, details screens, and colored picker rows throughout the app, while retaining three clearly labeled bottom finance actions.

One payment may cover several classifications, but the app cannot allocate it into separately displayed, related amounts. The user needs a Transaction split whose parts can have individual Categories, Tags, and Notes, contribute only their matching amounts to Budgets, and remain connected through their details. Archived Accounts must also leave the main financial selection without losing historical records or changing existing Budget scopes.

This is a new effort against an existing implementation. The previously implemented Personal Finance Design specification, its tickets, and its verification evidence remain historical records of that separate effort.

## Solution

Apply the new light-theme reference design across the native Android app. Expenses uses a red header and berry/red actions and amounts; Incomes uses green; Budgets and neutral destinations use blue. Use off-white backgrounds, white activity/card surfaces, gray secondary text and generic icons, prominent financial amounts, and the references' typography, spacing, and hierarchy. Match the reference layouts closely, with the adaptations explicitly described below.

Use a left drawer for Overview, Expenses, Incomes, Budgets, Categories and Tags, and Accounts, plus a Settings gear at the bottom. Remove the Overview/Expenses/Income navigation tabs. Inside Expenses and Incomes, provide By date and By category views. Keep Add expense, Add income, and Transfer money as three bottom actions on Overview, Expenses, and Incomes, using the old Overview image as their reference. Budgets keeps its own plus button.

The clock opens a shared right drawer containing month selection, active Account switches, and an active-only All accounts switch. It has no bottom action row. Its Account selection remains shared and persistent for Overview, Expenses, and Incomes. The same drawer opens on Budgets: month changes affect Budget progress, while Account switches affect only the main-ledger selection used when returning to other screens. Each Budget keeps its independent saved scope.

Transaction rows open details before editing. Ordinary editors use a large amount, a display-only currency circle, colored Category/Tags/Account/Date rows, picker sheets, a calendar, a numeric keypad, and Aa for the optional Note. Income or Expense direction comes from the creation action and can never be changed afterward. Save uses one top-right check; cancel and dirty-draft discard behavior are consistent.

Add Transaction split and Unsplit. An initial Transaction split allocates the original amount exactly into at least two positive Transaction split parts sharing an Account, date, and fixed direction. Each part has its own amount and optional Category, Tags, and Note, appears as a separate row with a gray branching Y-shaped marker, and opens details containing the current combined total and related parts. Per-part edits and deletion, group-wide Account/date changes, Budget matching, and draft-only Split/Unsplit behavior follow the rules below.

## Implementation Decisions

- Extend the implemented native Kotlin/Compose/Material 3 application, retaining Android 10 as the required platform, the single application module, unidirectional state/events, current repositories, and manual dependency construction. Do not replace the framework or broadly rewrite the architecture.
- Treat this specification as a delta to the implemented app. Reuse working month projections, Account selection persistence, finance validation, Budget matching, classification management, and Backup operations. Preserve all prior behavior except the explicit UI, archived-selection, immutable-direction, and Transaction split changes described here.
- Apply the reference palette, typography, spacing, flat full-width headers, white surfaces, generic field icons, and hierarchy throughout the app. The reference inventory and exceptions below define the visual target; do not copy sample financial data, profile identities, phone frames, or operating-system bars.
- Replace navigation between Overview/Expenses/Incomes tabs with the six-destination left drawer and Settings footer. The label Incomes is used for that destination; the finance direction remains Income. By date / By category tabs belong inside the directional destinations, not to global navigation.
- Keep the three labeled bottom actions on Overview, Expenses, and Incomes, with adequate content space so they do not obscure activity. Adapt to larger fonts by wrapping, growing, and stacking rather than clipping. Budgets uses its contextual plus; do not add the rejected Overview plus chooser or replacement Transfer action on Accounts.
- Retain one selected calendar month across financial destinations, initialized to the current local month. The clock opens the shared right drawer, including on Budgets; preserve the inward right-edge gesture and equivalent accessible actions. Use the reference's month-selection presentation without arbitrary date ranges.
- Show active Accounts only in the drawer, each with a selected-month Closing balance and switch. All accounts selects all currently active Accounts; clearing it clears the selection. It is on only when all listed active Accounts are selected. New Accounts remain unselected. The drawer has no bottom actions.
- Preserve an initially empty main Account selection and explicitly empty saved selections across process/app restarts. Zero selected Accounts means zero main balance, Income, Expense, and net, no matching main activity, and no Select Accounts prompt. Do not normalize empty to all or to a primary Account.
- Exclude archived Accounts from the main drawer and saved main selection. Prune an Account when archived and normalize stale saved selections against active Accounts when loading data. This applies even when viewing an earlier month. Retain read-only history under Accounts -> Archived; archiving does not delete financial records, zero historical balances, or remove existing Budget scope references/spending.
- Keep three distinct concepts: the main drawer's Account selection, a Transaction's mandatory Account, and a Budget's saved Account scope. Drawer changes made from Budgets persist for the main financial destinations but do not alter the All budgets/month header, Budget content, or saved scopes. Month changes still update Budget progress.
- Retain the established Closing balance calculation: signed Opening balance plus applicable Income, minus Expenses, minus outgoing Transfers, plus incoming Transfers through the selected month's final day. Respect the Opening balance date and never apply a future Opening balance early. Monthly flow totals continue to follow Transaction dates, independently of the Opening balance cutoff used for balances.
- Overview sums selected active Accounts' Closing balances and presents the agreed section order: combined balance, monthly Income/Expenses/net, Account cards, Budget progress, recent activity. Budget progress remains independently scoped and may be nonzero when the main Account selection is empty.
- By date starts selected, shows newest-first local day groups with deterministic same-day ordering, gray date/subtotal bands, and white rows. Keep the reference hierarchy of Category, lighter Tags, optional Note, and right-aligned amount, exposing relevant Account context. Empty optional metadata is omitted from details rather than replaced with fictional values.
- By category summarizes the same direction, selected month, main Accounts, and applicable Category/Tag filters, with largest totals first and Uncategorized where applicable. Category rows open the corresponding activity. Classify and filter each Transaction split part by its own fields. A Transaction split group total is contextual metadata, not another movement.
- Preserve existing Transfer membership: outgoing Transfers appear in Expenses when the source is selected; incoming Transfers appear in Incomes when the destination is selected; Overview shows a Transfer once when either endpoint is selected. Transfers are absent from By category and hidden by Category/Tag filters. Exclude them from Income, Expense, net, daily financial subtotals, and Budget spending.
- Transaction taps open details before editing. Ordinary details show the prominent amount, optional classification/Note, Account/date, back/edit/delete, and Split. Part details show that part's values, the current combined total, tappable related parts, and Unsplit. Preserve destructive confirmation; omit Make transfer conversion.
- Use parallel full-screen Income/Expense editors with the screenshot's prominent amount and colored Category/Tags/Account/Date rows. Tapping amount opens the numeric keypad; the configured currency is display-only. Aa opens the optional Note editor. Show only supported tools.
- Use bottom-sheet Category/Tags/Account pickers and a calendar date picker. Category is optional with None available; multiple Tags must remain compatible with the chosen Category and fixed direction; Account must be active. Preserve the most-recently-used active Account creation default, today's local date, and the original Account on edit. Changing another field must not silently choose a primary Account.
- Fix direction at creation through Add expense or Add income. Do not expose a direction selector or permit direction mutation in the public save/edit behavior for existing Transactions or Transaction split parts. Preserve archived classification references under existing edit rules, and remove incompatible Category-associated Tags when Category changes.
- Use one top-right save check and top-left cancel, omitting duplicate bottom save checks. A dirty draft requires discard confirmation. Show field-level validation and retain the draft for correction. Back/dismiss follows the same leave/discard semantics; it must not implicitly save.
- Extend the public Transaction application/repository boundary for Transaction split creation, related-part reads, per-part changes, group-wide Account/date edits, and Unsplit. Keep finance rules outside composables and expose complete observable outcomes. Reuse the existing transaction boundary rather than introducing screen-specific test interfaces.
- Initial Transaction split creation replaces one ordinary movement with at least two positive parts totaling exactly its original amount. All parts share Account/date/fixed direction and have independent optional Category/Tags/Note. The remaining amount must be zero to Save. Draft amounts may be unset while editing; invalid or incomplete allocations cannot commit.
- Follow the Split creation reference: toolbar cancel/save, shared Account/date above Split into, two initial white part cards with Amount/Category/Tags, and remaining-from-total feedback. Add Add part, per-card remove, and per-part Aa Note controls required by the agreed behavior. Amount uses the ordinary keypad. Income uses the corresponding green colors. Part is the domain noun even where the image uses Entry.
- Display parts as separate rows with a gray branching Y-shaped marker; do not substitute one collapsed payment row. Persist their relationship so part details can show the current combined total and navigate to related parts. Do not retain an additional countable original movement or count the group total as money.
- Per-part amount, Category, Tags, Note, and confirmed deletion affect only that part. Recalculate current totals after changes: EUR 40 + EUR 20 may become EUR 45 + EUR 20 = EUR 65 after an amount correction. Only initial allocation must preserve the pre-split amount. When one part remains, expose it as an ordinary Transaction without a split marker or stale relationship.
- Account/date edits apply to the complete related group in one validated change, with this effect stated clearly in the editor. Direction remains immutable. Preserve mandatory active Account, precise positive amounts, classification compatibility, and archived-history read-only rules for all affected data.
- Unsplit drafts one ordinary Transaction for the current sum of all related parts, preserving Account/date/direction and allowing an explicit final Category/Tags/Note choice. Do not arbitrarily take one part's classification. Initial Transaction split and Unsplit commit only on the final save check; cancel or failed validation leaves the previous complete ledger unchanged. Existing parts offer Unsplit, not Split again; nested Transaction splits are excluded.
- Make each committed multi-part transformation atomic with its affected financial records and relationships. Give new persisted concepts stable identities and deterministic timestamp behavior, preserve unaffected identities, and keep writes behind repositories. Plan and test identity transitions for allocation, per-part deletion, sole-survivor conversion, and Unsplit before changing persistence; this specification does not prescribe a table layout or which resulting record inherits the original identifier.
- Retain the implemented Budget model: named positive limit, nonempty explicit Account scope, optional multiple Expense Categories and Tags, OR within a restriction group and AND across active groups, each matching Expense amount counted once per Budget, independent overlapping Budgets, monthly recurrence, no carryover, no automatic scope expansion, and edits recalculating every month. Existing archived references remain in saved scopes.
- For a Transaction split, Budget/filter matching evaluates each part's Category/Tags independently. EUR 40 Groceries + EUR 20 Household contributes EUR 40 to Groceries, EUR 20 to Household, and EUR 60 to an unrestricted matching Budget. Multiple matching Tags cannot multiply a part. Income and Transfers do not count as Budget spending.
- Use one Budget card per definition with name, limit, month, saved scope, spent, remaining/overspent, and a conventional spent/limit progress bar. Omit the unexplained black marker and Non-monthly heading. The header is All budgets / selected month; plus opens a separate creation screen and a card opens editing. Retain the existing editor's finance fields and validation rather than introducing a new Budget lifecycle.
- Use blue neutral headers and white lists/forms for Accounts, Categories and Tags, Settings, and setup. Accounts has Active/Archived views; Categories and Tags has separate tabs. Transfer entry has a large amount, From Account, To Account, and Date, with distinct active endpoints and no Category/Tags/Note. Preserve existing history, management, setup, currency, Export/Import/reset, and confirmation capabilities.
- Keep finance data and Backup-owned settings in Room, presentation preferences excluded from Backups in DataStore, precise minor-unit money storage, explicit non-destructive migrations, and versioned serialization DTOs separate from persistence entities. Preserve all existing ledger and Budget data; no schema mutation is authorized by this documentation task.
- Extend supported Backup snapshots, validation, and reconciliation to preserve Transaction split relationships, current part values, shared fields, and transitions back to ordinary Transactions. Previously supported Backups remain importable as ordinary historical data; never infer Transaction splits from matching amounts/dates. Preserve supported legacy Budget conversion and provenance already settled by the earlier effort.
- Preserve stable-ID/newer-record Merge, idempotency, equal-timestamp divergence rejection, no deletion propagation, currency/reference validation, complete-snapshot export, and atomic Overwrite/cancellation/failure behavior. Before schema/Backup implementation, document and test how Transaction split membership and transitions reconcile under these existing rules. If a coherent result cannot be produced without inventing intent or propagating deletions, reject the conflicting Merge atomically under the existing conflict policy; do not silently duplicate an original payment, resurrect countable parts, or change group-shared fields piecemeal. Overwrite remains the explicit authoritative restoration operation.
- Use contextual empty messages, retain zero totals/no selection prompt for empty main scope, and keep errors beside the relevant fields without losing drafts. Long text wraps, surfaces grow, and bottom actions may stack at larger fonts. Preserve labeled controls, usable touch targets, scrolling, and accessible alternatives to gestures.

## Testing Decisions

- Assert externally visible behavior: committed and reloaded finance snapshots, precise balances/totals, returned validation outcomes, saved selection, displayed amounts and relationships, navigation, draft cancellation, and enabled/read-only controls. Avoid private-helper tests, composable implementation details, direct table assertions, and tests that only mirror implementation. Add only the application behavior needed to express the agreed operations through those boundaries.

## Out of Scope

- Application implementation, schema migration execution, APK packaging/installation, release, or deployment during this to-spec session.
- Creating implementation tickets, changing existing ticket statuses, or rewriting the already-implemented Personal Finance Design specification/evidence; ticket generation is reserved for the later to-tickets workflow.
- Framework replacement, a broad architecture rewrite, cloud profiles/accounts, bank integrations, online services, automatic synchronization, or network permission.
- Dark theme, a newer-Android testing requirement, Play Store distribution, biometric/app lock, or encrypted Backups.
- Free-text search, Transaction-to-Transfer conversion, location, recurring Transactions, reminders, photos, per-Transaction currency changes, or arbitrary date ranges.
- Income/Expense direction conversion or a direction selector, including during Transaction split, part editing, and Unsplit.
- Nested Transaction splits or Split again on an existing Transaction split part.
- Category-specific artwork, an icon picker or icon-related persistence/Backup fields; ordinary action/field symbols remain in scope.
- Category/Tags/Note on Transfers, or counting Transfers as earnings, spending, Category activity, or Budget consumption.
- Non-monthly Budgets, carryover, auto-created Budgets/scopes, effective-dated Budget edits, or new Budget deletion/stopping/archival policies.
- Fabricated sample finance data, profile identities, percentages, Updated just now text, copied phone frames/system bars, or literal reproduction of unsupported controls.
- Changing the established no-deletion-propagation Merge policy, stable identity/conflict rules, or atomic Backup behavior to simplify Transaction split storage. A concrete migration/reconciliation design is later implementation planning, constrained by this specification and existing ADRs.
- Requiring manual TalkBack/Switch Access testing that the user previously declined.

## Further Notes

- This specification was explicitly requested with to-spec after the grilling session. It is a separate artifact for the UI Reference Refresh effort, not a revision to the already-implemented [Personal Finance Design](../personal-finance-design/spec.md). Preserve that effort's tickets, answers, and verification. The status ready-for-agent is a triage label and does not authorize implementation in this documentation-only session.
- Source decisions are retained in the [grilling record](grilling.md). Later answers override earlier recommendations: separate marked rows replace the rejected collapsed-payment proposal; active-only selection replaces archived main selection; the Budget clock still opens the shared drawer; the three bottom actions replace the proposed contextual plus on the main financial screens; and fixed direction overrides the earlier proposal for group-wide direction changes.
- Use the root [glossary](../../GLOSSARY.md): Transaction split and Transaction split part are canonical domain terms. Split, Unsplit, Split into, Aa, and short part labels may be used as the agreed UI wording. A Transaction split is not a Transfer or an arrangement for shared debts.
- Applicable constraints remain the [local-first](../../docs/adr/0001-local-first-finance-data.md), [native Android](../../docs/adr/0002-native-android-boundary.md), [stable identity](../../docs/adr/0003-stable-entity-identities.md), [atomic Backup](../../docs/adr/0004-atomic-backup-import.md), and [distinct Transfer/balance](../../docs/adr/0005-transfers-and-account-balances.md) ADRs. Follow the existing [Android coding rules](../../AI-CODING-RULES.md) and [Android UI testing workflow](../../docs/research/ai-ui-testing.md).
- The old effort already settled [legacy Budget migration](../personal-finance-design/issues/06-named-recurring-budgets-with-selected-accounts.md): retain original identity, Category/month provenance, amount, and timestamps, linking the Accounts present at migration or included in the applicable old Backup. Later-created Accounts do not join saved scopes. Preserve that mapping rather than reopening it or conflating it with new Transaction split persistence planning.
- Existing source inspection confirms that current entry permits direction changes, Transaction taps edit directly, archived Accounts can be selected in the main drawer, and Budget editing is inline. Those are changes to make in future implementation, not reasons to reimplement the already-working finance model. No separate details, Transaction split, or Unsplit flow is assumed to exist already.
- The existing [integrated verification](../personal-finance-design/issues/evidence/11/verification.md) is historical evidence for the previous design. It is not new visual signoff or passing coverage for this effort. New evidence must reflect this specification and its intentional adaptations.
- The required storage/Backup design work does not mean the UI interview is reopened or authorize a migration now. Before future mutations, make identity transitions and coherent Backup reconciliation concrete and testable under the existing conflict policy. Surface any genuinely new product choice rather than silently changing agreed finance behavior.
